# Security Architecture & Policies

This document outlines the security architecture, Content Security Policy (CSP), threat mitigations, and credential hygiene practices implemented in Arsenic.

---

## 1. Security Architecture Overview

Arsenic is designed with a defense-in-depth security model:
- **No Persistent Database:** Arsenic does not store user profiles, passwords, or repository data in a database.
- **Server-Side Token Isolation:** Third-party OAuth client secrets and personal access tokens are stored strictly in server-side environment variables and are never transmitted to the browser.
- **Encrypted Client Sessions:** Authentication state is held in encrypted, signed HTTP-only cookies via `iron-session`.
- **Strict Input Validation:** All user-supplied parameters are validated against strict format constraints before any upstream API request is dispatched.
- **Comprehensive HTTP Security Headers:** Enforced at both the edge CDN level (`vercel.json`) and the Express application layer (`server/index.js` via Helmet).

---

## 2. Credential Hygiene & Secret Isolation

- **Environment File Isolation:** Local secret configuration is kept in `.env`, which is explicitly excluded from version control via `.gitignore` (`.env` and `.env.*`).
- **Template Hygiene:** Only safe placeholder values are committed in `.env.example`.
- **No Token Exposure to Client:** All requests to GitHub REST, GitHub GraphQL, and Google OAuth endpoints originate from backend serverless functions or the standalone Express server. The client-side React SPA receives only sanitized JSON payloads.
- **Secret Generation:** The session encryption key (`SESSION_SECRET`) must be a cryptographically secure random string of at least 32 characters.
  ```bash
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  ```
- **Secret Rotation:** Updating `SESSION_SECRET` invalidates all currently active user sessions immediately upon deployment, requiring users to log in again.

## 3. Content Security Policy (CSP)

Arsenic implements a restrictive Content Security Policy configured identically at the Vercel edge (`vercel.json`) and in Express (`server/index.js` via Helmet):

| Directive | Configuration | Rationale |
|:---|:---|:---|
| `default-src` | `'self'` | Disallows loading resources from untrusted origins by default. |
| `script-src` | `'self'` | Restricts executable scripts to local bundles generated by Vite. Zero external CDN scripts (such as unpkg, cdnjs, or jsdelivr) are loaded. |
| `style-src` | `'self' 'unsafe-inline'` | Permits locally bundled CSS and dynamic inline styles required by Recharts and layout transitions. |
| `font-src` | `'self' data:` | Relies on system font stacks (`ui-sans-serif, system-ui, -apple-system, Segoe UI, sans-serif` and `ui-monospace, SFMono-Regular, monospace`). No remote requests to Google Fonts or third-party CDNs are executed. |
| `img-src` | `'self' data: blob: https://avatars.githubusercontent.com https://lh3.googleusercontent.com` | Whitelists local images, base64 data URIs, canvas export blobs, GitHub user avatars, and Google profile avatars. |
| `connect-src` | `'self'` | All client-side API requests target local routes (`/api/*`, `/auth/*`). Upstream API traffic is handled server-side. |
| `form-action` | `'self' https://github.com https://accounts.google.com` | Restricts form submissions and OAuth redirects exclusively to the application origin and verified identity providers. |
| `frame-ancestors` | `'self'` | Protects against UI redressing and clickjacking by forbidding embedding inside external iframes. |
| `object-src` | `'none'` | Blocks legacy browser plugins (Flash, Java applets). |
| `base-uri` | `'self'` | Prevents unauthorized modification of document base URLs. |

### Additional Security Headers

- `X-Content-Type-Options: nosniff`: Prevents MIME-type sniffing.
- `X-Frame-Options: SAMEORIGIN`: Disallows framing from foreign origins.
- `Referrer-Policy: strict-origin-when-cross-origin`: Limits referrer leakage on cross-origin navigation.
- `Strict-Transport-Security`: Enforces HTTPS (`max-age=63072000; includeSubDomains; preload` in production).

## 4. How to Verify CSP in Browser DevTools

To verify that CSP directives are actively enforced and not generating violations:

1. Open the application in Google Chrome, Microsoft Edge, or Mozilla Firefox:
   - Production: [https://arsenic-rho.vercel.app](https://arsenic-rho.vercel.app/)
   - Local: `http://127.0.0.1:5173`
2. Open Developer Tools (`F12` or right-click → **Inspect**).
3. **Console Verification:**
   - Review the **Console** tab during page load, search, and comparisons.
   - Confirm that no `Refused to load... because it violates the following Content Security Policy directive` messages appear.
4. **Network Header Inspection:**
   - Switch to the **Network** tab and reload the page.
   - Select the main document request (the root URL or `/u/:username`).
   - In **Response Headers**, verify the presence of `content-security-policy`, `x-content-type-options`, and `x-frame-options`.
5. **Canvas Export Verification:**
   - Search a profile (e.g., `cgupta21`), click **Share Card**, and trigger both **PNG Export** and **PDF Export**.
   - Confirm that export rasterization completes without triggering CSP violations against `blob:` or `data:` URIs.

## 5. OAuth CSRF State Management & Dual Persistence

To prevent Cross-Site Request Forgery (CSRF) during third-party authentication:

1. **State Nonce Generation:** Upon initiating `/auth/github` or `/auth/google`, the backend creates a 48-character cryptographically random nonce.
2. **HMAC Signature:** The server signs the nonce with HMAC-SHA256 using `SESSION_SECRET`.
3. **Dual State Persistence:**
   - The signed state is stored in an HTTP-only `oauth_state` cookie (`SameSite=Lax`, `Max-Age=600`, `Secure` in production).
   - The state is also mirrored into the encrypted session (`req.session.oauthState`) to protect against environments that drop transient cookies during cross-site redirects.
4. **Verification & Cleanup:**
   - When the provider invokes the callback URL (`/auth/github/callback` or `/auth/google/callback`), the returned `state` parameter is verified against the signed cookie or session state.
   - Both tokens are cleared immediately upon validation to prevent replay attacks.

For more details on OAuth workflows, refer to the [Authentication & Sessions Documentation](authentication.md).

## 6. Input Validation & Parameter Sanitization

All incoming API requests are validated prior to initiating upstream requests:

- **GitHub Username Validation Regex:**
  ```javascript
  const GITHUB_USERNAME_REGEX = /^(?!.*--)[A-Za-z0-9](?:[A-Za-z0-9-]{0,37}[A-Za-z0-9])?$/;
  ```
- **Validation Enforcement:**
  - Applied across `/api/dashboard/:username`, `/api/summary/:username`, `/api/compare/:left/:right`, and crawler metadata routes (`/api/meta/:username`).
  - Inputs violating the format immediately return HTTP 400 (`Invalid username format`) without dispatching upstream requests.
  - Invalid requests do not consume guest search quotas.
- **Comparison Validation:**
  - `/api/compare/:left/:right` enforces that `:left` and `:right` are distinct and valid usernames before execution.

## 7. Client-Side Export Security & Canvas Safety

The developer summary card export relies on `html2canvas` and `jsPDF`. To ensure secure, reliable rasterization:

- **CORS Handling:** External avatar images specify `crossOrigin="anonymous"` to prevent canvas tainting.
- **Memory Protection:** The canvas element is passed directly to `jsPDF` rather than converting large base64 data URLs in intermediate memory buffers.
- **Font Availability:** Exports await `document.fonts.ready` prior to snapshotting to avoid layout reflows during capture.
